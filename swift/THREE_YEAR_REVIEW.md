# Historical product review: superseded decisions

**Parker's subsequent direction is authoritative:** remove background tracking entirely, preserve nearby/permission-based mode recommendations, and preserve the field-tested nearest-point discovery, thresholds, map tags and completion behavior. Do not implement this review's proposed discovery radius, replacement session model or removal of automatic recommendations. The current scope and verification are in [RELEASE_PREPARATION.md](RELEASE_PREPARATION.md). This document records the earlier analysis, not outstanding release blockers.

# Product review: ship it, then leave it alone for three years

This is a decision review, not permission to remove features. No substantive feature changes below have been implemented. The useful existing work remains: offline content, safer local saves, deterministic location tests, removed retired event/rating features, and the approved support-email change.

## Recommendation

Keep the illustrated map, searchable structure library, photos, favorites and optional guided tour. They are useful without any permission, account, server or calendar dependency. Make browsing the immediate default. Treat in-person tracking as a temporary **Start a canyon visit / End visit** session, requested by the visitor, rather than a persistent identity called Adventure Mode. Keep nearby background tracking during that explicit session, using When In Use authorization. Remove the Always upgrade and five-page onboarding after discussion. Fix visit-distance correctness before shipping. Do not rebuild the app's architecture or redesign the visuals to achieve this.

## Findings with consequences

1. **Location is requested before the user chooses to need it.** `OnboardingView.swift` has five pages; page 1 disables Next until the OS permission is either accepted or denied, while mode selection is page 2. A virtual reader must encounter GPS permission even though the final mode promises no location needed. Recommendation: open the map/library immediately, with a short optional introduction; ask for location only from Start visit. Tradeoff: lose the geographically inferred mode recommendation, which is much less valuable than a direct choice.

2. **Always authorization does not earn its extra prompt here.** The service uses standard `startUpdatingLocation`; it has no significant-change, region-monitoring or visit-monitoring registration to recover a session when the app is not running. The onboarding follow-up requires pressing Continue to request Always, even though declining it still works. Apple's SDK documentation for `requestWhenInUseAuthorization` explicitly permits a continuous background session started during active use to keep receiving updates until stopped or the app is killed. Recommendation: retain nearby background updates for an explicit active visit, request When In Use only, and explain that it is not unattended tracking after termination. This preserves pocketed-phone exploration without asking for broader permission. [Apple API reference](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization()). Evidence also inspected in the installed iOS SDK's `CLLocationManager.h`, requestWhenInUseAuthorization discussion.

3. **The tracking lifecycle can spend power for the wrong activity.** `LocationService.setupLocationManager` requests best accuracy, no distance filter and no automatic pauses. The 1.5-second throttle drops callbacks after Core Location delivers them; it does not throttle the GPS hardware. Adventure choice is persisted across launches and starts foreground GPS even far from the canyon. Worse, `MapBottomBar.notVisitingContent` starts the visual virtual walkthrough by toggling `isVirtualWalkthrough` without changing the service's Adventure mode. The app can display a virtual tour while still running real GPS. Recommendation: one explicit session state determines whether tracking runs; a virtual tour is a browsing route and never starts/retains tracking by accident. A modest distance filter can be considered after the correctness threshold is chosen; without physical testing, do not claim battery savings from a guessed accuracy setting. Tradeoff: visitors explicitly restart a visit rather than having tracking silently resume days later.

4. **Visit detection can award a structure hundreds of metres away.** The service checks an axis-aligned canyon rectangle, fix accuracy ≤50m, then awards the nearest map point if it is tagged. It never checks distance to that point. At the rectangle's southwest corner `(35.31307, -120.6560599752971)`, the nearest point is structure 26 at approximately 317m. A fresh isolated run of the production service confirmed `inside canyon true`, awarded structure 26, and measured 316.677m to the selected point. The broad box plus nearest-tag rule therefore misrepresents proximity even with an accurate GPS fix. Recommendation: require an explicit small discovery radius in addition to accuracy and geometry; 25m is a proposed starting value, not a field-validated guarantee. Keep saved progress intact. Tradeoff: conservative discovery can miss a visit under poor GPS; that is more honest than false discovery. A manual mark/unmark option would solve ambiguity but adds UI and should be decided, not slipped in.

5. **Several visible promises disagree with state semantics.** “Reset Visited Structures” in `PopUps.swift` invokes `DataStore.resetStructures`, which also removes favorites. Decide either to preserve favorites or label it a complete progress reset. The “Days” statistic only increases when discovering an unvisited structure; returning to already-visited structures on a later day does not count. Rename it “Discovery days” or drop that statistic. Ghosts 105/106 remain browseable but have no discovery coordinates, so do not promise that all six can be collected. Favorites themselves are cheap and useful; keep them.

6. **Map controls are less stable than their persistence suggests.** `AppState.configureMapSettings` changes satellite/number/zoom choices on tour transitions and canyon changes; `MapView.onAppear` invokes it again whenever an Adventure user returns to Map. A visitor's chosen map style can be replaced after reading a structure. Recommendation: persist actual user choices and keep temporary tour framing separate. The primary screen layout—Map, Structures, Settings—earns its place. Don't add another home screen. The tour and full-screen map currently use screen-percentage sizing, so compact devices and large text remain layout risks; address those in the later visual/layout pass rather than adding a new navigation framework now.

7. **Overlay state is functional but more complicated than necessary.** MainView separately draws detail, visit notification, custom alert and welcome overlays; only the welcome overlay has comprehensive mutual-exclusion checks. A discovery can interrupt an open detail/gallery. Recommendation: one presentation choice with visit notices queued or shown unobtrusively, not another layer on top of active reading. Existing main-actor ownership and the atomic store are adequate. The two mode booleans and parallel full-screen flags are a more meaningful simplification target than replacing Combine/SwiftUI or introducing a database.

8. **Offline content is the app's strongest durability property.** All research, map variants and photos ship locally; no sign-in, remote API or analytics backend is needed. Keep that. The full catalog is only 37 entries, so replacing the JSON snapshot with a persistence framework offers little value. Current recovery retains unreadable files, blocks unsafe/future-schema writes, and preserves visible state on failed saves. Legacy fallback may recover older rather than latest progress after corruption; no cloud backup promise should be made. Support and privacy URLs should be the only release-critical web dependencies, and neither should block app startup.

9. **Assets and supported destinations deserve bounded decisions.** The retained satellite image is 2000×4519 pixels: about 34.5 MiB as one uncompressed RGBA buffer, before rendering/cache overhead. Encoded file bytes are not memory usage. Eleven proven-unused exports were removed (10.77 MiB encoded); originals remain. Preserve the required numbered/no-number maps and photos; don't trade offline reliability for downloads. Downsampling thumbnail decoding could reduce peak memory later, but no measured memory or battery regression justifies an asset-format pipeline rewrite now. iPhone/portrait/iOS 16 is the actual tested configuration. Mac/Vision compatibility defaults are enabled but untested; review distribution availability and explicitly limit it to the supported phone experience before release, rather than implying those destinations are supported. Forced light appearance plus dormant dark-mode branches are avoidable complexity, but removing dark assets/code is a design decision for discussion.

## Smallest sensible pre-release change set

After Parker's decision: fix the discovery-distance rule and reset wording/behavior; make GPS session-driven with one source of truth; move permission to Start visit and remove the Always step; prevent virtual touring from retaining GPS; preserve user map choices. Keep the rest of the experience and offline assets. Leave a broader visual refresh, a framework migration and elaborate maintenance automation out of this release.

Already authorized and implemented: public support email is `parker.jones@live.com`; retired-feature removal, save safety and tests remain; the 11 unused iOS photo copies were removed while preserving source originals. Portable script defaults and brief source documentation were already completed before the scope correction; no hosted CI, synchronization system or further governance work was added.

Physical GPS, battery life and OS background delivery cannot be proven with these simulations. The deterministic suite does establish application decisions against actual content, and the new distance probe exposes a correctness gap the earlier happy-path coordinate replay did not cover. Passing a build is not a substitute for deciding these behaviors.

Verification of the already-authorized changes: data checks, production regression suite, final Debug build and a Release unsigned archive passed. `/Volumes/SSK Drive/Developer/Archives/PolyCanyon-three-year-review-20260908.xcarchive` was inspected: its compiled asset catalog omits the 11 unused photo names and retains all three NN map variants; its binary contains `parker.jones@live.com` and no old support address. These checks do not resolve the product findings above; they remain decisions before calling the app ready for a three-year freeze.
